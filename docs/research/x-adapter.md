# X adapter implementation research

Research date: 2026-08-31. Sources are first-party Alchemy and X documentation/source.

## Executive findings

The adapter needs **two independent authentication planes**, not one:

1. User-context OAuth 2.0 Authorization Code + PKCE for the X account whose activity is subscribed. The current X OpenAPI contract allows OAuth 2.0 user tokens on the create/validate Account Activity subscription operations with `tweet.read`, `users.read`, `dm.read`, and `dm.write`; add `offline.access` to receive a refresh token. [X OpenAPI](https://api.x.com/2/openapi.json) [X OAuth scopes and token lifetime](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code)
2. App-only Bearer authentication for listing/managing webhooks and app-level subscriptions, plus the app's API secret (consumer secret) at runtime to answer CRC challenges and verify deliveries. A user OAuth token does not replace these app credentials. [V2 Webhooks API](https://docs.x.com/x-api/webhooks/introduction) [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart) [App credentials](https://docs.x.com/x-api/getting-started/getting-access)

There is a first-party documentation conflict that should be covered by a live integration test: the Account Activity quickstart says subscription creation/checking requires OAuth 1.0a, while the current OpenAPI v2.168 declares both `OAuth2UserToken` and OAuth 1.0a `UserToken` for `POST`/`GET /2/account_activity/webhooks/{webhook_id}/subscriptions/all`. Implement OAuth 2.0 PKCE as requested, retain an extensible credential model for OAuth 1.0a fallback, and fail with an explicit diagnostic if X rejects the OAuth 2.0 subscription in a customer's access tier. [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart) [X OpenAPI](https://api.x.com/2/openapi.json)

Account Activity is not a free feature: X documents Pay Per Use and Enterprise access only. Pay Per Use is limited to three unique subscriptions and one webhook; Enterprise starts at 5,000+ subscriptions and 5+ webhooks. Account Activity Post deliveries count toward the monthly Post cap. [Account Activity overview](https://docs.x.com/x-api/account-activity/introduction) [X pricing](https://docs.x.com/x-api/getting-started/pricing)

## Package and Alchemy conventions

Recommended split:

- `distilled-x`: an Effect-native X API SDK generated from X's official OpenAPI, with hand-written credential/protocol/error modules. This mirrors `@distilled.cloud/github`, whose package exposes `Credentials`, protocol, errors, retry, generated services, and per-service entry points, and resolves its credential Effect per request so rotated tokens work without rebuilding the Layer. [Distilled GitHub package](https://github.com/alchemy-run/distilled/tree/cc93bf364f93840f008e0a50e8edbaab63348a9d/packages/github) [GitHub credentials source](https://github.com/alchemy-run/distilled/blob/cc93bf364f93840f008e0a50e8edbaab63348a9d/packages/github/src/credentials.ts) [GitHub protocol source](https://github.com/alchemy-run/distilled/blob/cc93bf364f93840f008e0a50e8edbaab63348a9d/packages/github/src/protocol.ts)
- `alchemy-x`: declarative resources, the `X.providers()` collection, the Alchemy Auth Provider, and runtime event-source integrations. Alchemy providers are Effect Layers; a resource implementation supplies lifecycle operations such as `diff`, `reconcile`, `delete`, and `list`, while `providers()` bundles the resource collection and implementations. [Provider guide](https://alchemy.run/infrastructure-as-code/provider/) [Custom provider guide](https://alchemy.run/infrastructure-as-code/custom-provider/)

The `alchemy-x` public surface should initially contain `Webhook`, `AccountActivitySubscription`, `consumeAccountActivity`, `providers()`, and explicit credential layers for tests/programmatic use. `AccountActivitySubscription` should depend on the `Webhook` output so destroy order removes subscriptions before deleting the webhook. This follows Alchemy's current GitHub split between a declarative webhook resource and a host-specific event source that provisions it at deploy time and verifies deliveries at runtime. [Alchemy GitHub Webhook](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/GitHub/Webhook.ts) [GitHub repository event source](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/GitHub/RepositoryEventSource.ts) [Cloudflare host integration](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/Cloudflare/Workers/GitHubRepositoryEventSource.ts)

Alchemy Auth Providers implement five Effect-returning operations—`configure`, `login`, `logout`, `prettyPrint`, and `read`—and are registered by name inside the cloud's `providers()` Layer. Credentials are lazy Effects; a Profile stores non-secret method configuration in `~/.alchemy/profiles.json`, while secrets live under `~/.alchemy/credentials/{profile}/`. `read` runs under a cross-process lock, which is important when refreshing and persisting OAuth credentials. [Auth Providers](https://alchemy.run/environments/auth-providers/) [Custom Auth Provider](https://alchemy.run/environments/custom-auth-provider/) [AuthProvider source](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/Auth/AuthProvider.ts)

## OAuth 2.0 PKCE lifecycle

Use `https://x.com/i/oauth2/authorize` for authorization and `POST https://api.x.com/2/oauth2/token` for both code exchange and refresh. Authorization parameters are `response_type=code`, `client_id`, an exactly registered `redirect_uri`, space-delimited `scope`, random `state`, `code_challenge`, and `code_challenge_method`; X accepts `S256` or `plain`, so the adapter should use `S256`. The authorization code expires after 30 seconds. [Authorization Code + PKCE reference](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) [User-token walkthrough](https://docs.x.com/fundamentals/authentication/oauth-2-0/user-access-token)

For a public client, token exchange sends form-encoded `code`, `grant_type=authorization_code`, `client_id`, `redirect_uri`, and `code_verifier`. A confidential client authenticates token requests with HTTP Basic over `client_id:client_secret`. Refresh uses the same token endpoint with `grant_type=refresh_token`; logout can revoke either token at `POST https://api.x.com/2/oauth2/revoke`. [User-token walkthrough](https://docs.x.com/fundamentals/authentication/oauth-2-0/user-access-token)

Access tokens last two hours by default. X issues a refresh token only when `offline.access` was authorized, so it is mandatory for unattended Alchemy deploys; persist every successful refresh response before returning the fresh access token. [Authorization Code + PKCE reference](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) [Alchemy refresh pattern](https://alchemy.run/environments/auth-providers/#refresh-in-practice)

For Account Activity, request `tweet.read users.read dm.read dm.write offline.access`; the first four come from the operation's current OpenAPI security requirement and the last enables refresh. `GET /2/users/me` can identify and persist the authenticated user's ID and requires user-context authentication. [X OpenAPI](https://api.x.com/2/openapi.json) [Authenticated-user lookup](https://docs.x.com/x-api/users/lookup/quickstart/authenticated-lookup)

X callback URLs must be allow-listed exactly (including trailing slash), with at most ten per app. Production uses HTTPS; local development should use `http://127.0.0.1`, explicitly not `localhost`. Therefore a local Alchemy callback server should bind a fixed `127.0.0.1` URI configured by the user in the X Developer Console. Do not assume Alchemy's provider-owned `https://alchemy.run/auth/callback` relay can be reused without an X app and relay configuration. [X app callback rules](https://docs.x.com/fundamentals/developer-apps) [Alchemy's Cloudflare OAuth client](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/Cloudflare/Auth/OAuthClient.ts)

CI must avoid browser prompts. Follow Alchemy's convention of choosing an `env` auth method when `CI=true`; accept an OAuth access/refresh session or an app owner's pre-generated tokens from environment variables, while keeping OAuth interactive for local `alchemy login`. [Auth Providers: env fallback](https://alchemy.run/environments/auth-providers/#the-env-fallback) [X credential security guidance](https://docs.x.com/x-api/getting-started/getting-access)

App-only Bearer tokens are a separate flow: use a Developer Console Bearer token or `POST https://api.x.com/oauth2/token` (no `/2`) with Basic-authenticated API key/secret and `grant_type=client_credentials`. X says only one app Bearer token is outstanding and repeated creation returns the existing token, so cache it. [X OAuth API reference](https://docs.x.com/fundamentals/authentication/api-reference) [App-only authentication](https://docs.x.com/fundamentals/authentication/oauth-2-0/application-only)

## Automatic webhook and subscription lifecycle

X's v2 webhook operations are app-scoped: `POST /2/webhooks` creates, `GET /2/webhooks` lists, `PUT /2/webhooks/{id}` triggers CRC validation/re-enables, and `DELETE /2/webhooks/{id}` deletes. The returned webhook object contains `id`, `url`, `valid`, and `created_at`. All lifecycle reads require an app-only Bearer token. [V2 Webhooks API](https://docs.x.com/x-api/webhooks/introduction) [Create](https://docs.x.com/x-api/webhooks/create-webhook) [List](https://docs.x.com/x-api/webhooks/get-webhook) [Validate](https://docs.x.com/x-api/webhooks/validate-webhook) [Delete](https://docs.x.com/x-api/webhooks/delete-webhook)

Recommended `Webhook` reconciliation:

1. Observe by persisted `webhookId`; if state is missing, list and adopt an exact URL match before creating, avoiding `DuplicateUrlFailed`. If observed but `valid=false`, call `PUT` and re-read. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart)
2. Create only after the public handler is deployed, because `POST /2/webhooks` immediately performs CRC and fails registration when the endpoint cannot answer correctly. Model the deployed URL/secret as Alchemy dependencies. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart)
3. Treat a URL change as replacement because X exposes no URL-update operation; `PUT` only validates. On Pay Per Use, create-before-delete will exceed the one-webhook quota, so replacement must either delete-then-create with an explicit downtime/risk warning or stop with a clear manual-migration error. [V2 Webhooks API](https://docs.x.com/x-api/webhooks/introduction) [Account Activity limits](https://docs.x.com/x-api/account-activity/introduction)
4. Delete by persisted ID and treat already-missing as success. Implement `list` from `GET /2/webhooks` for Alchemy account-wide enumeration. This matches the idempotent observe/ensure/delete shape of Alchemy's GitHub webhook provider. [Alchemy GitHub Webhook source](https://github.com/alchemy-run/alchemy/blob/901859886e0fb6130fb7bb5aff397e6db72332f9/packages/alchemy/src/GitHub/Webhook.ts)

`AccountActivitySubscription` creates/checks `POST`/`GET /2/account_activity/webhooks/{webhook_id}/subscriptions/all` in user context, lists subscriptions with app Bearer auth at `GET .../all/list`, and deletes a specific user with app Bearer auth at `DELETE .../subscriptions/{user_id}/all`. Treat `DuplicateSubscriptionFailed` as converged and persist both `webhookId` and `userId`. Only the `/all` product exists; event selection cannot be narrowed. [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart) [Account Activity overview](https://docs.x.com/x-api/account-activity/introduction)

## CRC, signatures, and runtime behavior

The webhook URL must be public HTTPS with no explicit port, handle both GET and POST, acknowledge deliveries with HTTP 200 within ten seconds, and be at most 200 characters. [V2 Webhooks API](https://docs.x.com/x-api/webhooks/introduction) [Create webhook](https://docs.x.com/x-api/webhooks/create-webhook)

For a CRC GET containing `crc_token`, compute `HMAC-SHA256(app API secret, crc_token)`, Base64-encode the binary digest, prepend `sha256=`, and return JSON `{ "response_token": "sha256=..." }`. The key is the API/consumer secret—not a Bearer or user access token. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart)

For POST delivery verification, compute the same Base64 HMAC over the **raw request body** and compare it in constant time with `x-twitter-webhooks-signature`; parse JSON only after verification. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart)

The official pages disagree on periodic CRC timing: the quickstart says hourly, while the overview describes a 30-minute check only when no successful validation occurred in the prior 24 hours and invalidation after prolonged failure. The implementation must therefore keep CRC handling permanently available rather than scheduling around either interval. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart) [V2 Webhooks API](https://docs.x.com/x-api/webhooks/introduction)

## Account Activity payloads and operational caveats

Every delivery is keyed by `for_user_id` and contains one of `tweet_create_events`, `tweet_delete_events`, `favorite_events`, `follow_events` (including unfollow types), `block_events` (including unblock types), `mute_events` (including unmute types), `user_event` revoke, `direct_message_events`, `direct_message_indicate_typing_events`, or `direct_message_mark_read_events`. Payloads include legacy-shaped Post/User objects, and long-form Posts put full content in `extended_tweet.full_text`; use a tagged union while preserving unknown fields for forward compatibility. [Account Activity payload reference and examples](https://docs.x.com/x-api/account-activity/introduction)

The API delivers all supported activity for a subscription, not home-timeline data. A revoke event automatically removes the user's subscription. Interactions between two subscribed users, multiple apps sharing a URL, and occasional delivery behavior can produce duplicates; distinguish subscription copies with `for_user_id` and deduplicate by event ID. [Account Activity overview](https://docs.x.com/x-api/account-activity/introduction) [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart)

Replay can recover Account Activity events from the preceding 24 hours through `POST /2/account_activity/replay/webhooks/{webhook_id}/subscriptions/all`; X documents additional recency constraints and emits a `replay_job_status` completion/incomplete event. It is useful as a later resource/action, but it is not required for initial automatic registration. [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart)

## Minimum validation matrix

- Unit-test PKCE state/verifier/challenge, confidential/public token requests, refresh persistence, and revoke against recorded X-shaped responses. [X OAuth user-token flow](https://docs.x.com/fundamentals/authentication/oauth-2-0/user-access-token)
- Unit-test CRC and POST signatures against exact raw bytes, malformed/missing headers, and constant-time comparison. [Webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart)
- Provider-test create/adopt/revalidate/delete, duplicate subscription convergence, out-of-band deletion, and the one-webhook URL-change path. [Alchemy provider testing guide](https://alchemy.run/infrastructure-as-code/custom-provider/#test-the-lifecycle) [X webhook limits](https://docs.x.com/x-api/account-activity/introduction)
- Run one gated live test proving OAuth 2.0 user tokens can create and validate an Account Activity subscription, because X's human quickstart and machine-readable OpenAPI currently disagree. [Account Activity quickstart](https://docs.x.com/x-api/account-activity/quickstart) [X OpenAPI](https://api.x.com/2/openapi.json)
